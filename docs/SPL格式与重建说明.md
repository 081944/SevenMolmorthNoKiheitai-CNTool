# 7W `.spl` 格式与可变长重建说明

本文档记录目前对 `seven_data_link/rpgdata/output/*.spl` 的完整容器解析结果。
结论来自 `unpak/CDIMAGE.BIN` 解包出的 321 个原版 SPL、PCSX2 DebugServer
运行时内存，以及 IDA Pro 中的 `SLPS_250.25.i64` 静态交叉引用。

## 1. 文件总览

所有 321 个脚本都以 `01 00 00 00` 开头，文件尾固定为：

```text
00 00 00 00 00 00 00 00 10 00 00 00 FF FF FF FF
```

文件由以下部分组成：

```text
u32  version/type = 1
u32  reserved     = 0
u32  data_offset  = 文件中数据区起点
u32  reserved     = 0
byte 8 * VM instruction records
      data directory
      typed data blocks
      16-byte footer sentinel
```

`data_offset` 总是 `0x10 + 8*n`，所以 `0x10..data_offset-1` 是定长 8 字节
指令流。最后一条通常是全零记录；解析时应以 `data_offset` 为边界，不能用
文本扫描结果推断代码区长度。

### 1.1 指令记录

指令记录按小端解释为 `<u16 opcode, u8 arg2, u8 arg3, u32 value>`。当前样本中
出现的 opcode 为：

```text
00, 02, 04, 05, 06, 08, 09, 0C, 0D, 10, 11, 12, 13, 14, 15, 16
```

`0x09`、`0x0C`、`0x0D` 的部分 `value` 是 VM 指令索引；目标脚本中例如
`0x00000F96` 对应的代码地址为 `0x10 + 0xF96*8 = 0x7CC0`。其它 opcode
的参数是变量、常量、资源 ID 或控制值，重建时必须原样保留。指令区不是
字符串区，不能对其中的 CP932 偶然字节做替换。

## 2. 数据目录

`data_offset` 处的 16 字节头为：

```text
<u32 kind=2, u32 entry_count, u32 directory_end, u32 reserved=0>
```

随后有 `entry_count` 个 8 字节目录项：

```text
<u32 entry_id, u32 instruction_index>
```

`directory_end = align16(0x10 + entry_count*8)`，它是从数据区起点算的
相对偏移。目录之后立即进入类型化数据块；目录中没有文件绝对地址，因此
数据块增长时不需要修改目录。

## 3. 类型化数据块

每个块都有统一的 16 字节头，`size` 包含块头，并且按 16 字节对齐：

```text
<u32 kind, u32 count, u32 size, u32 reserved>
byte[size-16] payload
```

321 个原版文件的块顺序完全一致：

```text
3, 9, 14, 4, 5, 6, 7, 8, 11, 13, 15, 10, 12
```

未知块的 payload 可以按 `size` 原样搬运；这也是重建器在不需要理解每个
游戏逻辑字段时仍能保证完整 round-trip 的关键。已确认的块约束如下：

| kind | 已确认内容 |
| --- | --- |
| `3` | 辅助 CP932 NUL 字符串池；`count` 固定为 0，通常为空，少数脚本包含若干字符串。没有外部重定位引用。 |
| `9` | 16 字节记录数组；记录字段 `+0x08` 是 type-10 字符串池的相对偏移，其余字段为资源/参数元数据。 |
| `10` | 主 CP932 字符串池；`count` 是被引用的非空字符串数，payload 为 NUL 结尾字符串及零填充。 |
| `11` | 16 字节记录数组；记录字段 `+0x08` 同样是 type-10 字符串池相对偏移，`+0x0C` 等字段可能是数值/属性，必须保留。 |
| `13` | 一个 16 字节记录。 |
| `14` | 16 字节记录数组。 |
| `15` | 16 字节记录数组或空块。 |
| `7` | 16 字节记录数组。 |
| `12` | 许多脚本中是 8 字节记录数组；少数尺寸不满足简单定长数组，按 opaque payload 保留。 |
| `4`,`5`,`6`,`8` | 资源/几何/运行参数块，记录尺寸随脚本变化；当前重建不修改 payload。 |

### 3.1 字符串引用规则

type-9/type-11 的记录布局至少满足：

```text
record + 0x00: u32 id/metadata
record + 0x04: u32 type/metadata
record + 0x08: u32 string_offset   # 相对 type-10 payload 起点
record + 0x0C: u32 flags/value     # 原样保留
```

例如原版 `10020_h_tam.spl`：

```text
data_offset             = 0xA510
type-10 block payload   = 0xA510 + 0xA50 + 0x10 = 0xAF70
type-11 id=0x23 offset   = 0x538
目标句文件绝对偏移       = 0xAF70 + 0x538 = 0xB4A8
```

字符串偏移指向字符串首字节；若偏移非零，其前一个字节必须是 NUL。type-10
的 `count` 与 type-9/type-11 引用合并后的唯一偏移数一致，这是验证引用表
没有漏项的强约束。

## 4. 目标句的运行时确认

原版镜像在 PCSX2 DebugServer 中运行到：

```text
文件基址      0x00428740
目标文件偏移  0x0000B4A8
目标内存地址  0x00433BE8
```

PCSX2 在 `PC=0x00128608` 暂停，`0x00128608` 是文本排版/显示入口；其调用者
`0x0016A568` 在 `0x0016A6E8` 调用该函数，并从脚本状态对象取出字符串指针。
IDA Pro 的交叉引用显示该调用点和 `sub_128608` 的其它调用点，日志保存在
`temp/ida_spl_analysis.log`。这与离线偏移 `0xB4A8` 完全吻合，证明文本池
不是固定宽度槽，而是运行时直接使用的可变长 NUL 字符串。

## 5. 重建算法

`tools/text_7w.py write` 现在按以下流程工作：

1. 校验头、指令区边界、目录、全部块尺寸和文件尾 sentinel。
2. 收集 type-3/type-10 字符串池中的真实字符串和行边界；忽略代码区及其它
     二进制块中偶然符合 CP932 的字节。
3. 读取候选文件的“原文 | 译文”双栏。先验证候选偏移处的原文；偏移过时但
   原文能在结构化字符串池中找到时，自动选择距离原偏移最近的真实行并记录
   `relocated`。找不到的旧启发式假阳性记录为 `ignored`。
4. 以 CP932/自定义字库槽编码译文，替换完整行，不受原行字节数限制；保留
   原 NUL 和对齐填充。
5. 重新串接两个字符串池，更新 type-10 块的 `size`，按 16 字节补零。
6. 按旧偏移映射更新所有 type-9/type-11 的 `+0x08` 字符串引用；其它块和
   指令流逐字节搬运。字符串池变长或变短导致的后续块移动无需额外绝对地址
   修复，因为块引用都是池内相对偏移。
7. 重新写入固定 16 字节 footer，并再次执行结构校验。

未修改的 SPL 通过该流程必须逐字节相同；这也是回归测试的首要条件。

## 6. 验证结果

使用 `temp/CDIMAGE_ORIGINAL`（从 `unpak/CDIMAGE.BIN` 重新解包）验证：

- 321/321 个原版 SPL 可解析。
- 321/321 个空修改 round-trip SHA/字节完全相同。
- 结构化提取共 17,766 行；目标句稳定为 `0xB4A8`。
- 目标句重复 5 次形成超长译文时，字符串池自动扩展，type-11 引用正确指向
  新字符串，未触碰后续块内容语义。
- 现有 321 份翻译候选演练：`changed=13710`、`relocated=146`、
  `ignored=111`、`unencodable=0`、`mismatch=0`。

## 7. 当前边界

容器级格式、字符串池、引用重定位和可增长重建已经完整覆盖；`kind=4/5/6/8`
等资源块内部的游戏业务字段以及所有 VM opcode 的人类可读命名尚未逐条命名。
它们在重建中按长度和原始字节保留，不影响根据任意长度译文生成可加载 SPL。
下一阶段若要做脚本编辑器，再针对这些 opaque 块和 opcode 建立语义层即可。
