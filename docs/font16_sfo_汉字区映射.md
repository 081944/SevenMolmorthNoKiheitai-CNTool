# font16.sfo 汉字区映射说明

本文档记录 7W 字库 `font16.sfo` 的**按区（CP932 lead byte）映射**机制，是
汉化"字形槽位 → CP932 编码"对应关系的基础。所有结论以**干净原版字库**为准：

```text
temp/font16_PRISTINE.sfo   （从原始 CDIMAGE.BIN 提取，SHA256 4f9e280a…）
```

> ⚠️ 不要使用 `unpacked/CDIMAGE_*` 下的 font16.sfo——它们可能已被 build
> 流程污染（装入过中文字形）。引用前先核对 SHA256。

> ⚠️ 重要更正：**对白渲染不使用 font16.sfo**，而是 `common.fhm` sub0 字库。
> sub0 的 lookup 表基址与 font16.sfo 不同（`0x88→0x177`、`0x8A→0x2F1`），
> 因此同一 CP932 槽位在两套字库中的索引不同（如 `0x8A9A`：font16→idx910、
> sub0→idx907）。汉化对白时按 sub0 的 lookup 计算索引，见
> `docs/common_fhm_sub0字库.md`。

## 总体结构

字库按 **CP932 的 lead byte（区）** 分组存储。每个字形槽位由一个"区 + 区内序号"唯一确定：

```
CP932 编码 = (lead 高字节, trail 低字节)
字库索引 = 区基址 + 区内 trail 偏移
```

### 索引表 A 字段 = 区的 lead byte

索引表位于文件偏移 `0x210`，每条 4 字节 `(A: u16, B: u16)`。

- **A 低字节 = 该槽位字形的 CP932 lead byte**（即所在的区）
- A 高字节恒为 `0x10`（高度/格式标志，暂不关注）
- B 决定字形数据在文件内的偏移：`start = B * 0x10 + 8`

## 区内 trail 映射规则

**同一区内，索引顺序严格对应 CP932 的 trail 字节递增序列**（跳过 0x7F）。

- 完整区（188 项，如 0x89）：trail 从 **0x40** 到 **0xFC**（0x40~0x7E + 0x80~0xFC，跳过 0x7F）
  - 索引631 = 0x8940，索引632 = 0x8941，…，索引818 = 0x89FC
- **0x88 区（94 项）：trail 从 0x9F 开始**（CP932 里 0x8840~0x889E 是无字区）
  - 索引537 = 0x889F（亜），索引538 = 0x88A0，…，索引630 = 0x88FC
- 0x98 尾区（52 项）：trail 从 0x40 起，只收 52 个

## 完整的 index ↦ CP932 映射表

已生成：

```text
work/font/index_to_cp932.csv     （3400 条：index, cp932_hex, lead, trail）
```

生成规则（当前正确版，含 0x7F 空位）：

```python
starts = {0x81:97, 0x88:537, 0x89:631, 0x8A:820, ...}   # 各区起点索引
start_trail = {0x81:0x41, 0x88:0x9F, 其它:0x40}          # 各区起始 trail
for 存在索引 idx（按 lead 分组）:
    trail = start_trail[lead] + (idx - 各区起点)
    # 包含 0x7F：0x7F 对应一个缺失占位索引，映射表不含它
```

## ✅ 关键修复：trail 0x7F 空位（2026 实测确认）

**发现的问题**：某个汉字区在 trail `0x7F` 处有一个**缺失的占位索引**（空字形）。
之前映射用"跳过 0x7F"的 trail 序列，导致整个区错位。

**实测例子（0x89 区）**：
- 索引 693 = 円（CP932 = 897E）
- 索引 694 = **空位**（CP932 trail 0x7F 对应，records 中缺失，A=0xFFFF 占位）
- 索引 695 = 園（CP932 = 8980）

**正确规则**：`trail = 起始trail + (idx − 区起点)`，**包含 0x7F**（0x7F 对应一个
空占位索引，该索引无字形、不可写入中文）。

各区的起始 trail：
| lead | 区起点索引 | 起始 trail |
|---|---|---|
| 0x81 | 97 | 0x41 |
| 0x88 | 537 | 0x9F |
| 0x89 / 0x8A~0x97 | 631(+188n) | 0x40 |
| 0x98 | 3466 | 0x40 |

**全部锚点已通过**：idx97=8141、537=889F(亜)、560=88B6、693=897E(円)、
695=8980(園)、716=8995、900=8A90、1200=8C42。

完整映射表 `work/font/index_to_cp932.csv`（3400 条）已按此规则重建。
缺失索引（0x7F 空位等）**不进入映射表**，alloc 也不会把中文分配到这些索引。

## 🔍 权威通用公式（2026 实测确认，取代分段规则）

在 `font16.sfo` 偏移 `0x10` 处有一个 **256 × u16 的 lead-byte 查表**（与
`0x210` 起的索引表 `(A,B)` 不同）。`font16.sfo-7w.md` 曾把 `0x10-0x210` 误当
"lead-byte lookup 区"，实测确认它就是游戏用来查字形的基准表。游戏的字形寻址
**唯一且通用**为：

```
index = lead_lookup[lead] + trail           # trail 为 CP932 低字节原值 (0x40..0xFC)
其精确逆变换：                          trail = index - lead_lookup[lead]
```

对任意索引，`lead = (A & 0xFF)`，`lead_lookup[lead]` 取偏移 `0x10+lead*2` 的 u16。
该公式对全部 3400 个有效索引成立（含各占位 0x7F 空位，不产生冲突），并可用
锚点验证：`0x8141→97`、`0x824F→285`、`0x8340→449`、`0x889F→537`、`0x897E→693`、
`0x8980→695`、`0x8C42→1198`。

### 关键修复（0x82 区起始 trail）：0x4F 而非 0x40

旧映射假定 **0x82 区从 trail 0x40 开始**（对应索引 285），这是错的。按权威公式
反推，索引 285 的真实 trail 是 `285 − lead_lookup[0x82] = 285 − 206 = 79 = 0x4F`，
即 0x82 区实际从 **0x824F** 开始（0x8240..0x824E 在本字库为未定义/洞）。旧 CSV
若给 0x82 区槽位写 `0x82yy` 会错位，游戏会解析到错误索引 → 显示错误字形。

`work/font/index_to_cp932.csv` 已按 `trail = index − lead_lookup[lead]` 全量重建；
`tools/font_hack_7w.py alloc` 与 `tools/text_7w.py` 均已改为直接从 `font16.sfo`
读取权威公式（不再依赖旧 CSV 的分段 trail 假设）。
